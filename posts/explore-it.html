Chapter 1 — Exploratory Testing

Posted on 2026-08-09

Two questions every test should answer

When writing tests, there is no need to create a large number of them. What matters is that they answer two questions:

# Question What it looks for
1 Does the program work the way it was designed to? the expected behaviour, the requirements as they were written
2 Are there any other risks? everything nobody thought about when the feature was designed

Thinking about the first question: the program needs to normalize its inputs and to have a way of checking everything that could turn into an error.

Why exploratory testing helps

Exploratory testing helps a lot with both questions, because in this kind of testing we use the insight gained from the first test to design the next one. For example:

If a system has a security rule that blocks the user after 5 failed password attempts, you now have an insight about the blocking mechanism. So you think:

If I type the correct password, log out, and try to log in again, will the counter of 5 failed attempts be reset?

That is why exploratory tests are more flexible and more effective than a unit test, which is fixed to a single rule.

Exploration is not passive

To make exploratory testing effective, you cannot simply run the tests you planned in a passive way, writing nothing down. You need to take notes of:

  • doubts that came up during the session;
  • the flows you went through;
  • anything else you need to remember later.

Then you pass those notes on to someone else, so that the team's knowledge about the program keeps growing.

Chapter 2 — Charter your exploration

Posted on 2026-08-12

What you need before you start testing

This chapter teaches that when you start testing, you need these three things:

# Item What it can be
1 Objective the goal: it can be a module, a feature or some requirement from somebody
2 Tools it can be a data set, a technique or a configuration
3 Information you are looking for such as security, performance, reliability, risks, etc.

How to write a correct charter

To write a correct charter, you need to avoid two extremes:

  • a description that is too specific about what to test, because then it becomes a unit test;
  • a huge description, because then you waste too much time and it becomes impossible to test.

Chapter 3 — Observe the details

Posted on 2026-09-01

Observation is the tester's main skill

We often believe the system is right only because the result of some function returns what we want to see, but that is not true. Because of that, one of the most important abilities for whoever tests software is observation.

It is easy to let things go by unnoticed if you are not looking for them.

Superficial tests

A lot of times we settle for superficial tests without really "digging deeper" in search of errors, such as:

  • generating a report but not checking its content to see whether the information is true;
  • logging into the system but not checking whether it is actually validating the password, and so on.

When the system is hard to observe

If the system is not easy to test or to monitor, it is possible to do these simple things with scripts or native tools, in order to check memory usage, the flow and the number of requests, and many other things that affect the system indirectly.

Besides everything written above, we also have the system's own logs, which show directly the logs, the errors and the warnings about the application.
