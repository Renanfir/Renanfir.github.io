Chapter 1 — Exploratory Testing

Two questions every test should answer

When writing tests, there is no need to create a large number of them. What matters is that they answer two questions:

# Question What it looks for
1 Does the program work the way it was designed to? the expected behaviour, the requirements as they were written
2 Are there any other risks? everything nobody thought about when the feature was designed

Thinking about the first question: the program needs to normalize its inputs and to have a way of checking everything that could turn into an error.

Why exploratory testing helps

Exploratory testing helps a lot with both questions, because in this kind of testing we use the insight gained from the first test to design the next one. For example:

If a system has a security rule that blocks the user after 5 failed password attempts, you now have an insight about the blocking mechanism. So you think:

If I type the correct password, log out, and try to log in again, will the counter of 5 failed attempts be reset?

That is why exploratory tests are more flexible and more effective than a unit test, which is fixed to a single rule.

Exploration is not passive

To make exploratory testing effective, you cannot simply run the tests you planned in a passive way, writing nothing down. You need to take notes of:

  • doubts that came up during the session;
  • the flows you went through;
  • anything else you need to remember later.

Then you pass those notes on to someone else, so that the team's knowledge about the program keeps growing.
